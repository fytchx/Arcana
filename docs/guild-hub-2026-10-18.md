# Arcana Guild Hub · preview implementation checkpoint (2026-10-18)

## Source and isolation

Feature branch: feature/guild-hub-2026-10-18, based on feature/arcana-balanced-home-v137-2026-10-18 at 61c21e4, not the outdated default-branch frontend. **Do not merge or deploy to the live domain without mobile validation and a migration/backup review.** The existing legacy guild directory remains unchanged.

Guild Hub is an Arcana community feature. It does not query, claim to update, or impersonate the IdleArc game's actual guild system. All writes use the existing account data volume, never a new isolated production identity database.

## Experience

- The new guild directory lists approved guilds, plus a creator's own pending registration. Every Arcana account may register one active guild; creation starts pending and is not styled as official until a moderator or administrator approves it.
- Tags are exactly four ASCII letters, case-insensitive and uppercase. Unregistered player tags are allowed in account profiles and rendered plain gray. Pending and registered guilds reserve their tags. Registered styles only render when a profile's server-held guild membership ID matches a registered guild. On approval, existing unregistered users with the same four letters lose the conflicting free tag, preventing impersonation.
- Guild owners customize name, bio, recruitment status, tag color and finish (solid/glow/gradient), and a layered SVG crest builder with 25 center marks, 25 secondary marks, 10 outlines, 10 border geometries and 4 independent colors. Shapes are fixed server-approved indexes, not arbitrary SVG uploads.
- Public pages display avatar, bio, roster, recruitment/application status, and public announcements. Members can make discussion posts; leaders/officers can post announcements, accept/decline applications and moderate members. Owners assign officers, transfer ownership, edit identity and upload icons. Owners must transfer ownership before leaving.
- Square page icon uploads are cropped on-device to 128×128, re-encoded WebP and size checked on the server. They remain pending; a moderator approves the icon separately. Previously approved icons remain visible during replacement review.
- Moderators use the Guild Approval Queue for registration and icon approval, rejection, and audit entries. API mutations are validated server-side against Discord-authenticated Arcana roles and require same-origin requests. Guild posts are rate-limited. All state is stored in JSON under the existing account directory using the shared serialized atomic-write queue.
- Profile cards and general-chat message names show badges alongside player names. Unregistered tags stay gray; matched registered guild membership gets the approved crest.

## API

- GET /api/guild-hub: approved guild directory plus requester-owned review items.
- POST /api/guild-hub/register: apply to register a guild, requires signed-in Arcana account.
- GET /api/guild-hub/:id: public profile plus member-appropriate roster, board and pending applications.
- PATCH /api/guild-hub/:id: owner-controlled guild bio, crest and identity styling.
- POST /api/guild-hub/:id/icon: pending upload, not immediately public.
- POST /api/guild-hub/:id/apply: player request to join.
- PATCH /api/guild-hub/:id/applications: leader/officer approval.
- PATCH /api/guild-hub/:id/members: role changes, transfer, removal, departure.
- POST /api/guild-hub/:id/posts and DELETE /api/guild-hub/:id/posts?postId=: bounded board.
- GET /api/guild-hub/moderation and PATCH /api/guild-hub/:id/moderation: role-gated moderation.

## Scope and next release gates

This is a community board with announcements, not a full real-time Discord clone. No private DMs, image attachments in posts, voice rooms, push notifications, event RSVP, multiple channels, spam automation, guild invitations, or game-linked guild rosters are claimed. Add these after core membership and moderation survive QA; never promise in-game guild data without an authorized official API.

The existing legacy guild-recruitment feed is independent; migration should be opt-in and non-destructive. Before release, confirm the actual Railway-mounted account directory, back up its profiles, verify Guild Hub on a private staging instance with a copied test dataset (no live customer writes), exercise all moderation and member flows on Android-sized Chromium, audit file storage growth/rate limits, verify role visibility and cross-account access, and re-run the entire source/mobile suite. Do not mistake a successful deploy for successful end-user testing.
